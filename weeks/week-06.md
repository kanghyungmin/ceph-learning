## Day 26 — RBD와 RGW 개념 확장

### 0~25분: 개념 이해

CephFS는 경로와 POSIX 파일 연산, RBD는 가상 블록 장치, RGW는 S3/Swift API를 제공합니다. 객체 API의 key는 일반적인 공유 파일 경로와 같은 의미가 아닙니다.

### 25~45분: 실행 전 확인

공유 IDE 작업공간, 단일 DB 디스크, 로그 아카이브 세 사례를 골라 인터페이스·접근 방식·일관성 요구·권한 준비 항목을 비교하세요. S3 쓰기는 자격 증명 없이 시도하지 않습니다.

### 45~80분: 실습

공식 RBD/RGW 문서를 읽고 CephFS/RBD/RGW를 파일·블록·오브젝트 API로 비교합니다. `qks-block`을 Ceph RBD라고 단정하지 않습니다. RGW 프로세스가 있다고 S3 자격 증명까지 있다는 뜻도 아닙니다.

완료 기준: DB 디스크, 공유 워크스페이스, S3 백업 대상의 선택 근거 설명.

### 80~100분: 결과 해석

DB라서 무조건 RBD처럼 절대 규칙을 쓰지 말고 애플리케이션 지원과 운영 요구를 근거로 선택하세요. 여기서는 RBD/RGW 사용 권한이나 Endpoint를 새로 확인하지 않았습니다.

### 100~120분: 확인 질문과 기록

**질문:** RGW 서비스가 보이면 S3 버킷을 바로 만들 수 있나요?

<details>
<summary>생각한 뒤 해설 보기</summary>

아닙니다. S3 Endpoint, 네트워크, 사용자 자격 증명과 정책 확인이 필요합니다.

</details>

## Day 27 — 처음부터 다시 배포하고 검증 설계

### 0~25분: 개념 이해

재현 가능한 구성은 사람이 기억한 명령이 아니라 검토 가능한 YAML과 검증 절차로 남습니다. 독립된 두 번째 실습은 기존 데이터에 기대지 않고 과정을 이해했는지 확인합니다.

### 25~45분: 실행 전 확인

아래 종합 실습 YAML로 새 PVC와 Pod를 생성하세요. 기존 2개 Pod와 추가 2개 Pod의 노드 분산 조건은 label별로 따로 적용됩니다. 파일 쓰기·반대편 읽기·재시작 후 읽기를 직접 설계하세요.

### 45~80분: 실습

기존 실습 데이터를 지우지 않고 별도 이름의 두 번째 PVC와 Pod로 Day 2~4를 재현합니다. YAML의 namespace와 모든 참조 이름을 검토한 뒤 적용합니다.

완료 기준: 생성 → 공유 확인 → Pod 교체 → 영속성 확인을 스스로 수행. 추가 PVC 사용량을 기록.

#### 독립된 종합 실습 시작

```bash
kubectl apply -f labs/03-capstone.yaml
kubectl rollout status deployment/capstone-reader -n ceph-lab --timeout=180s
kubectl get pods -n ceph-lab -l app=capstone-reader -o wide
kubectl get pvc shared-workspace capstone-workspace -n ceph-lab
```

두 PVC의 volumeName이 다른지 확인한 뒤 `app=capstone-reader`로 Pod 변수를 설정하세요. 공유 파일을 `/data/capstone-proof.txt`로 만들고 반대편 읽기와 rollout restart 후 읽기를 수행합니다. 기존 Day 3 파일은 새 볼륨에 없어야 합니다. 추가 요청 용량은 1Gi입니다. 이 파일을 재적용할 때 두 번째 PVC를 별도로 확장했다면 원본 요청량도 맞추세요.

### 80~100분: 결과 해석

새 PVC는 기존 파일이 없는 것이 정상입니다. 기존 PVC와 다른 volumeName인지 확인하세요. cluster quota나 노드 자원이 부족하면 추가 실습을 멈추고 원인을 기록합니다.

## Day 28 — 종합 진단 과제

### 0~25분: 개념 이해

진단 능력은 에러 메시지를 외우는 것보다 가설을 증거로 좁히는 능력입니다. 잘못된 StorageClass는 새 PVC로 해결하는 편이 명확하며 Bound PVC의 Class를 변경하는 방식으로 접근하지 않습니다.

### 25~45분: 실행 전 확인

Day 8 YAML을 복사해 이름을 day28-missing으로 바꾸세요. 20분 타이머로 이벤트와 SC 목록을 조사한 뒤 원인을 쓰세요. 올바른 새 PVC YAML은 dry-run으로 검증해도 됩니다.

### 45~80분: 실습

Day 8의 없는 StorageClass PVC를 새 이름으로 재현합니다. 20분 이내에 이벤트에서 원인을 찾고 올바른 Class를 사용하는 새 PVC YAML을 제시합니다. 바인딩된 PVC의 StorageClass를 직접 변경하지 않습니다.

완료 기준: 증거와 원인·해결책을 분리해 기록하고 잘못 만든 미바인딩 PVC 정리.

### 80~100분: 결과 해석

삭제할 것은 자신이 만든 미바인딩 오류 PVC입니다. 다른 PVC를 지우거나 default StorageClass를 바꿀 이유가 없습니다. 해결 전후의 리소스 이름을 구분해 적으세요.

### 100~120분: 확인 질문과 기록

## Day 30 — 최종 점검과 후속 실습 설계

### 0~25분: 개념 이해

이 과정의 성과는 사용·관찰·진단입니다. 설치와 실제 장애 복구는 추가 환경에서 검증해야 할 별도 능력입니다. 스스로 설명하기와 다시 실행하기를 함께 평가해야 합니다.

### 25~45분: 실행 전 확인

질문마다 0점=설명 불가, 1점=개념 설명, 2점=근거 명령과 결과까지 설명으로 평가하세요. 부족한 세 항목을 골라 재실습 계획을 세우세요. 정리는 백업·복원 확인 후 선택적으로 수행합니다.

### 45~80분: 실습

아래 질문을 자료 없이 설명하고 어려운 항목은 복습합니다.

- PVC/PV/StorageClass/CSI는 각각 무엇인가?
- RWO와 RWX는 무엇을 보장하고 무엇을 보장하지 않는가?
- CephFS·RBD·RGW는 RADOS와 어떻게 연결되는가?
- MON·MGR·OSD·MDS는 어떤 역할인가?
- Pool·PG·CRUSH는 어떻게 연결되는가?
- Pending과 Permission denied는 어디서부터 조사하는가?
- 스냅샷과 백업은 어떤 실패 범위를 보호하는가?

후속 과정은 별도 클러스터에서 구축 → Pool 생성 → 복제/CRUSH 변경 → OSD 장애 → recovery/backfill → 인증 관리 순으로 진행합니다. VM·디스크 등 환경 요건은 선택한 Ceph 배포 방식에 맞게 별도로 산정합니다. 60시간 과정 완료를 운영 변경 숙련과 동일시하지 않습니다.

### 80~100분: 결과 해석

자료를 참고해 복습해도 됩니다. 최종 평가는 개념 설명과 실습 증거를 연결하는 데 목적이 있습니다. 현재 운영 환경의 장애 주입은 후속 과정으로 넘깁니다.
