## Day 11 — 서비스와 계층 이해

### 0~25분: 개념 이해

RADOS는 분산 객체 저장 기반입니다. 그 위에 파일 인터페이스 CephFS, 블록 인터페이스 RBD, 오브젝트 API RGW가 놓입니다. MON은 맵과 quorum, MGR은 관리·모니터링, OSD는 데이터 저장, MDS는 CephFS 메타데이터를 담당합니다.

### 25~45분: 실행 전 확인

인증된 CLI에서 status를 실행하고 service 영역의 항목을 역할 표에 옮기세요. versions가 거부되면 권한 부족을 기록하고 다른 명령으로 권한을 우회하지 않습니다.

### 45~80분: 실습

공식 입문 문서를 읽고 RADOS, CephFS, RBD, RGW 및 MON·MGR·OSD·MDS를 정리합니다.

```bash
ceph -s
ceph versions
```

`ceph versions`는 이번 과정에서 처음 확인하는 명령입니다. 거부되면 에러를 기록하고 status 조회만 진행합니다. 현재 모든 명령의 권한이 보장된 것은 아닙니다.

완료 기준: 저장 인터페이스와 클러스터 데몬의 역할을 구분.

### 80~100분: 결과 해석

CephFS가 사용되어야 MDS가 필요한 것처럼 인터페이스마다 필요한 서비스가 다릅니다. 버전 숫자는 실제 관측 결과로 기록하고 예전 채팅의 숫자를 현재값으로 쓰지 마세요.

### 100~120분: 확인 질문과 기록

## Day 12 — health와 quorum

### 0~25분: 개념 이해

quorum은 MON들이 일관된 클러스터 상태를 유지하는 합의에 관련됩니다. OSD의 up은 실행·통신 상태, in은 데이터 배치 참여 상태입니다. 둘은 별도 축이므로 down과 out을 같은 뜻으로 읽지 않습니다.

### 25~45분: 실행 전 확인

status 출력에서 MON 수와 quorum, MGR 상태, OSD up/in, PG 상태를 각각 적으세요. health detail이 비어 있거나 경고가 있으면 상태와 함께 확인 시각을 기록하세요.

### 45~80분: 실습

```bash
ceph -s
ceph health detail
```

MON quorum, active/standby MGR, OSD up/in, PG 상태를 읽습니다. `HEALTH_OK`가 곧 백업이나 모든 애플리케이션의 정상 상태를 보장하지는 않습니다.

완료 기준: 출력 각 항목을 설명하고 확인 시각을 기록.

### 80~100분: 결과 해석

HEALTH_WARN이 곧 모든 I/O 중단은 아닙니다. 반대로 HEALTH_OK가 응용프로그램 정합성이나 백업 존재를 보장하지도 않습니다. 경고 발생 시 학습자가 설정을 바꾸지 말고 의미를 조사합니다.

### 100~120분: 확인 질문과 기록

**질문:** OSD가 up이면서 out일 수 있나요?

## Day 13 — OSD와 장애 도메인

### 0~25분: 개념 이해

CRUSH 트리는 OSD의 위치와 계층을 나타냅니다. 복제본을 어느 수준으로 분산할지는 Pool의 CRUSH rule과 연결됩니다. 트리에 host가 있다고 모든 Pool이 host 단위 장애를 견디도록 설정되었다고 단정할 수 없습니다.

### 25~45분: 실행 전 확인

트리에서 host별 OSD 개수를 세고 weight와 reweight 열을 구분하세요. 전체 트리가 크면 학습 예시로 host 두 개만 골라 그리세요. 실제 rule 정의를 못 봤다면 장애 도메인은 추가 확인 필요라고 적으세요.

### 45~80분: 실습

```bash
ceph osd tree
```

root → host → OSD 구조와 weight를 확인합니다. 호스트 수·OSD 수를 기록하고 디스크 장애와 호스트 장애의 차이를 설명합니다. OSD out/down 명령은 실행하지 않습니다.

완료 기준: 현재 CRUSH 트리에서 확인 가능한 장애 도메인을 그림으로 정리.

### 80~100분: 결과 해석

OSD 개수와 호스트 개수는 다릅니다. 디스크 세 개가 한 호스트에 몰리면 호스트 장애 시 동시에 잃을 수 있습니다. topology 관찰과 Pool 내구성 보장은 다른 단계입니다.

### 100~120분: 확인 질문과 기록

**질문:** 복제본 세 개만 있으면 호스트 하나 장애에 항상 안전한가요?

## Day 14 — Pool과 용량

### 0~25분: 개념 이해

Pool은 배치·복제/EC 정책을 적용하는 논리 단위입니다. replicated size는 복제본 수이고 min_size는 I/O 허용에 필요한 최소 복제본 수와 관련됩니다. EC는 k개의 데이터와 m개의 코딩 조각을 사용하는 방식입니다.

### 25~45분: 실행 전 확인

qks-ceph 데이터 Pool 한 개를 골라 유형·size·min_size·pg_num·crush_rule을 적으세요. ceph df에서 raw 영역과 Pool 영역을 구분해 표를 만드세요. size는 예시값을 대입하지 말고 실제 출력에서 읽으세요.

### 45~80분: 실습

```bash
ceph df
ceph osd pool ls detail
```

Pool의 replicated/erasure 유형, size/min_size, PG 수를 확인합니다. raw used, stored, available을 구분하세요. 복제 배수 외에도 메타데이터·정렬·압축·EC 등으로 실제 사용량이 달라질 수 있습니다.

완료 기준: 한 Pool을 골라 논리 데이터와 물리 사용량 차이를 설명.

### 80~100분: 결과 해석

이상적인 replicated 3배나 EC (k+m)/k는 개념 비교용입니다. 실제 사용량에는 메타데이터 등 추가 요소가 있습니다. MAX AVAIL은 단순 raw free 합과 다를 수 있습니다.

### 100~120분: 확인 질문과 기록

**질문:** raw free가 남으면 모든 Pool이 그만큼 더 쓸 수 있나요?

## Day 15 — PG와 배치

### 0~25분: 개념 이해

파일이나 블록 이미지는 내부적으로 여러 객체로 표현될 수 있습니다. 객체는 Pool 안의 PG로 매핑되고 CRUSH와 맵을 통해 OSD 집합에 배치됩니다. PG는 파일 하나와 같은 단위가 아닙니다.

### 25~45분: 실행 전 확인

전체 PG 상태 개수를 확인하고 active+clean 의미를 문장으로 쓰세요. 문서 사례에서 degraded, undersized, peering을 찾아 상태·영향·추가 확인할 항목으로 분류하세요.

### 45~80분: 실습

```bash
ceph pg stat
ceph osd pool ls detail
```

object → PG → OSD 관계, active와 clean의 의미를 학습합니다. degraded, undersized, peering은 문서 사례로 비교합니다.

완료 기준: MON이 파일 데이터를 직접 저장하는 서버가 아닌 이유와 CRUSH의 역할을 설명.

### 80~100분: 결과 해석

active는 I/O를 처리할 수 있는 상태와 관련되고 clean은 요구된 복제 상태가 충족된 상태를 나타냅니다. PG 상태는 조합되어 표현되므로 단어 하나만 보고 판단하지 않습니다.

### 100~120분: 확인 질문과 기록
